Plugin Packages (Hubs)

How to distribute multiple modules in a single Master Package

The "Independent Citizen" Architecture

Even when inside a parent package, child plugins are First-Class Citizens. They communicate directly with the Kernel via OsExtensionInterface, and do not use the parent plugin as a middleman. The parent is just a folder organizer (Hub).

What is a Plugin Hub?

Suppose you want to distribute a "Clinic Management Package". It has a module for Patients, another for Doctors, and another for Finance. Creating one gigantic, monolithic plugin is terrible for code maintenance.

Instead, OS 2.0 allows you to create a Hub (Package). The Hub is a parent plugin that physically contains multiple completely independent child plugins.

Why is this amazing?

The developer of the child plugin doesn't need to know they are inside a package. They just sign the OsExtensionInterface contract as usual, and the OS 2.0 recursively discovers them, booting each one individually!

Configuring the Parent Plugin (Hub)

To transform a standard plugin into a Package Hub, you just need to declare the getSubPluginsPath() method. This tells the OS 2.0 Plugin Discoverer where to look for child modules.

namespace DomainSystem\Plugins\clinic_pack;

use DomainSystem\Core\Plugin\AbstractPlugin;
use DomainSystem\Core\Contracts\OsExtensionInterface;

class Plugin extends AbstractPlugin implements OsExtensionInterface
{
    // The magical method that enables the HUB feature!
    public function getSubPluginsPath(): string
    {
        // Inform the OS where your children are located
        return __DIR__ . '/bundled_plugins';
    }

    // Standard OS 2.0 Contract (The Hub itself can also have logic)
    public function osRegister(OsConnector $os): void {
        $os->listenHook('admin.menu');
    }
    
    public function osBoot(OsRuntime $runtime): void {
        // Hub logic...
    }
}

Developing the Child Plugin

This is the best part: the child plugin code is exactly identical to a standalone root plugin. You don't need to import the parent or talk to the Hub. The child talks directly to the OS 2.0 Kernel.

namespace DomainSystem\Plugins\patients;

use DomainSystem\Core\Plugin\AbstractPlugin;
use DomainSystem\Core\Contracts\OsExtensionInterface;

class Plugin extends AbstractPlugin implements OsExtensionInterface
{
    // I am a child, but I can demand my own database link!
    public function osRegister(OsConnector $os): void
    {
        $os->requireLink('core.db');
        $os->listenHook('router.register');
    }

    public function osBoot(OsRuntime $runtime): void
    {
        // My routes are registered globally, independently of the Hub!
        $runtime->onHook('router.register', function($router) {
            $router->addRoute('GET', '/patients', [Controller::class, 'index']);
        });
    }
}

Example: Physical Distribution

Notice how the parent has a plugin.json and each child also has its own plugin.json. Each folder acts as an isolated micro-service within the system.

src/Plugins/
 └── clinic_pack/                   (The Hub)
      ├── Plugin.php                (Returns getSubPluginsPath)
      ├── plugin.json               (Hub Manifest)
      │
      └── bundled_plugins/          (The Hub's internal ecosystem)
           ├── patients/            (Child 1)
           │    ├── Plugin.php      (Normal OsExtensionInterface)
           │    └── plugin.json     (Manifest for versioning)
           │
           ├── finance/             (Child 2)
           │    ├── Plugin.php      (Normal OsExtensionInterface)
           │    └── plugin.json     (Manifest for versioning)
           │
           └── appointments/        (Child 3)
