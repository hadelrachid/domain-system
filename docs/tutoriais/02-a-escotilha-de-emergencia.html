Priority System & Firewalls

Advanced Security and Priority Hooks in Domain-System OS

The "Emergency Hatch" Concept

Sometimes, your plugin needs to act as a definitive Firewall, guaranteeing it will run after everyone else or before everyone else. This is where the Hook Priority System comes in.

How to Use Priorities

In the new OS 2.0 contract, when calling $runtime->onHook(), you can pass a third parameter indicating the priority.

If no priority is passed, the OS defaults to 0. Negative priorities run earlier, positive priorities run later. The higher the number, the later it runs.

public function osBoot(OsRuntime $runtime): void
{
    // Default execution (priority 0)
    $runtime->onHook('admin.menu', function($menu) { ... });

    // High Priority - Runs LATER (e.g., Priority 999)
    $runtime->onHook('router.before_dispatch', function($uri) { ... }, 999);

    // Low Priority - Runs EARLIER (e.g., Priority -10)
    $runtime->onHook('router.before_dispatch', function($uri) { ... }, -10);
}

The "Emergency Hatch" Pattern (Firewall)

Look at how the SystemAdmin plugin acts as the ultimate security net of the Kernel. It listens to the router.before_dispatch event with priority 999.

Why? Because the Auth Plugin might handle authentication at priority 0. If Auth crashes, gets disabled, or fails, the SystemAdmin will trigger its Emergency Hatch and block unauthenticated users from accessing the /admin panel, forwarding them to the emergency login.

// The Emergency Hatch (Safety Net)
$runtime->onHook('router.before_dispatch', function($uri) use ($sessionManager) {
    if (str_starts_with($uri, '/admin') && !str_starts_with($uri, '/admin/emergency')) {
        
        // If no session exists at this exact moment (even after other plugins tried)
        if (!$sessionManager->has('user_id')) {
            header("Location: " . BASE_URL . "/admin/emergency");
            exit; // Terminates the OS securely
        }
    }
}, 999); // Guaranteed to be the last one checking!

Execution Flow Security

The priority mechanism in the OsRuntime prevents "race conditions" where two plugins compete for the same action. It acts as an orchestrator.

  • Phase 1 (Priority < 0): Preparation plugins, logging setups, modifying request data.
  • Phase 2 (Priority 0): Standard logic execution. Almost 90% of your Hooks will sit here.
  • Phase 3 (Priority > 0): Firewalls, overrides, emergency hatch exits.
